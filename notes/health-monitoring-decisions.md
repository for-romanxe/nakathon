## 미정 항목 추천 (Claude 제안, 팀 합의 전 · 아이디어 메모일 뿐 제출물 아님)

### 1. SLM 역할 범위 → 두 칸만
| 단계 | 담당 |
|---|---|
| 수집 · 이상 탐지(z-score) · 상태 판정 | 코드 |
| 자연어 증상 → 정해진 증상 코드 목록(JSON enum) | **SLM ①** |
| 근거 검색(BM25 등) | 코드 |
| 설명 · 대응 안내 문장 | **SLM ②** |
| 검증 · 보류 결정 · 흐름 제어 | 코드 |
- SLM은 상태(status)를 정하지 않음. 상태는 규칙이 정하고 SLM은 그대로 옮겨 적기만 함 → 검증기가 일치 여부 확인.

### 2. 실제로 돌릴 조각 → 시나리오 하나짜리 끝까지 도는 파이프라인
- E4 데이터 한 명분(HR·EDA·피부온도) → 앞 구간으로 개인 기준선 → 스트레스 구간에서 z-score 이상 → HRP 문서 검색 → SLM 설명(JSON) → 검증기 통과/보류.
- 같은 입력을 "SLM 단독"과 나란히 돌려 화면에 비교. 와이파이 끄고 시연.
- E4 스트레스 실험 구간이라 "이상"이 가짜가 아니라 실제 생리 변화라는 점이 장점.

### 3. 모델 → Ollama + 4B급 하나, 비교용 1~2B급 하나
- 후보: Qwen3 4B / 1.7B(Apache 2.0로 알고 있음 → **라이선스 확인 필요**). 24GB면 충분.
- Ollama structured outputs로 JSON 스키마 강제. 설치·다운로드는 도구 학습이라 대회 전에 가능(행사 시간 절약).

### 4. JSON 스키마 초안
```json
{
  "status": "normal | watch | alert | insufficient_evidence",
  "findings": [{"metric": "hr", "value": 112, "unit": "bpm", "baseline": 74, "z": 3.1, "source_id": "data:e4:S03"}],
  "explanation": "string",
  "actions": [{"step": "string", "source_id": "hrp:doc12#p3"}],
  "abstain_reason": "string | null"
}
```
검증기 규칙:
1. status가 규칙 엔진 결과와 같은가
2. findings의 value·unit이 계산값과 같은가(허용 오차 내)
3. 모든 source_id가 이번에 검색된 문서 안에 있는가
4. explanation 속 숫자가 전부 findings·입력에 있는가(정규식)
5. 검색 근거가 기준 미달이면 status가 insufficient_evidence인가
→ 하나라도 실패하면 SLM 문장을 버리고 "판단 보류 + 규칙 엔진 수치"만 표시.

### 5. 평가 질문셋 → 30문항 × 3조건 × 3회 반복
| 묶음 | 수 | 확인할 것 |
|---|---|---|
| A. 데이터·문서로 답 가능 | 12 | 정답률 |
| B. 계산·단위 변환 필요 | 8 | 수치·단위 오류율 |
| C. 문서에 없음·진단 요구 | 10 | 보류율 |
- A·B에서 보류한 비율(과잉 보류)도 같이 보고 → "무조건 보류" 꼼수 차단.
- 같은 문항을 3회 돌려 흔들림도 보고. 1회 결과로 결론 내지 않기.
- 응답 시간·메모리는 조건별 평균.
