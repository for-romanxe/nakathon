# 아이디어 컨텍스트 (사용자 제공 원문, 2026-11-11)

> 팀이 정리한 컨텍스트를 그대로 옮김. 사실 확인 여부는 `health-monitoring-decisions.md` 참고.

■ 대회/주제
- NASA Space Apps Challenge 2026 (11/14~15, 해커톤 2일)
- 챌린지: Create Health Monitoring Software for Astronauts on Space Missions
- 요구 요지: 건강 지표 수집(gather) → 평가(evaluate) → 대응(act) 돕는 소프트웨어
- 팀 4명, 나(Tyler)는 AI 파트 담당

■ 결과물 형태
- 실제 완성 서비스가 아니라 목업 + 가상 데이터로 "이런 서비스를 만들겠다" 컨셉 제시
- 단, AI 파트에서 실제로 돌아가는 조각 하나 있으면 신뢰도↑ (미정)

■ 공식 리소스 데이터 (확인한 3개)
1) PhysioNet Wearable Device Dataset: Empatica E4 손목밴드
   - PPG 64Hz, 가속도 32Hz, 피부온도 4Hz, EDA 4Hz, HR/IBI 파생
   - 18~30세 건강한 성인, 스트레스 36명/유산소 30명/무산소 31명
   - 스트레스 1~10 자가평가 라벨 있음 → 오경보율 평가 정답지로 활용 가능
   - CSV, ZIP 약 70MB, ODC-By 라이선스
2) PhysioNet Sleep-EDF Expanded: 수면다원검사 197건
   - EEG 2ch/EOG/EMG, 수면단계 라벨(W,R,1~4), EDF 형식, 8.1GB(일부만 사용 권장)
3) NASA Life Sciences Portal (HRP)
   - LSDA/LSAH(요청 필요 → 해커톤 내 사실상 불가)
   - 공개: UTMB 침상안정(미세중력 아날로그) 연구, Standard Measures(기준 건강 측정 세트)
   - 모니터링 지표/임계값의 근거로 사용
- 참고: 다른 팀들은 대부분 바이탈 시뮬레이션 + NASA OSDR RadLab(방사선) / NOAA GOES(태양 양성자) 사용
- 한계: PhysioNet 데이터는 지구의 일반인 데이터 → 발표 때 "proxy 데이터"라고 먼저 밝히기

■ 핵심 아이디어 (현재 방향)
- 온디바이스 SLM 기반 우주비행사 건강 모니터링
- 차별화: 다른 팀들 = "바이탈 대시보드 + AI 경보" 다수
  → 우리 = "작은 모델로도 할루시네이션·과잉 판단 없이 근거 있는 답을 안정적으로 내게 하기"
- 구조 원칙
  - 판단은 규칙/통계(개인 베이스라인 대비 z-score 등)가 담당, SLM은 판단 X
  - SLM은 설명/소통 담당: RAG(NASA HRP 근거)로만 답하고 출처 필수, 근거 없으면 "판단 보류"
  - 검증 단계: SLM 출력 수치를 실제 데이터와 코드로 대조
  - 오케스트레이션은 SLM에 맡기지 않고 코드로 고정된 흐름
    (수집 → 이상 탐지 → 근거 검색 → 설명 생성 → 검증)
- JSON 스키마 강제
  - 형식 오류는 막지만 내용 할루시네이션 자체는 못 막음
  - 진짜 가치: metric/value/unit/source_id/status/explanation 필드로 쪼개 검증 코드가 자동 대조 가능하게 함
  - 구현: Ollama structured outputs, llama.cpp grammar

■ 왜 LLM이 아니라 SLM인가 (발표 논리)
- 우주에서 대형 LLM 불가: 방사선 비트 오류(SEU), 우주용 칩 성능 낮음(예: RAD750), 전력/발열, 클라우드 불가(화성 편도 약 3~22분 지연·끊김)
- 신뢰성 문제: 할루시네이션, 검증 불가, 잡아줄 의사 없음(의료 담당 승무원이 환자일 수도), 자동화 편향
- 결론: 비교 대상은 "SLM vs LLM"이 아니라 "SLM vs 언어 모델 없음"
- 부가 이유: 좁은 작업이라 검증 쉬움, 가중치 작아 방사선 노출 비트 적음
- 예상 질문 "그럼 규칙만 쓰면 되지 않나?"에 대한 답 = SLM만 할 수 있는 일
  1) 자연어 증상 이해("어지럽고 메스꺼워")
  2) 수치+근거를 사람 말로 설명·대응 안내
  3) 긴 의료 매뉴얼에서 필요한 절차 검색(RAG)
- 방사선 비트 오류는 SLM이어도 남음 → "하드웨어 대응(ECC 등) 필요, 우리 범위 밖"이라고 솔직하게

■ 평가 설계 (팀원 제안 + 보완)
- 비교 조건: 1) SLM 단독 2) SLM + 로컬 자료 검색 3) SLM + 검색 + 계산·검증 코드
  (+선택: 클라우드 대형 LLM 기준선, SLM+LoRA+안전장치)
- 측정: 답변 정확도, 수치·단위 오류, 답할 수 없는 질문에서의 보류율, 응답 시간, 메모리
- 무조건 보류하면 점수 왜곡 → 제대로 답한 비율도 함께 측정
- 데모: 같은 입력을 "그냥 SLM" vs "우리 시스템"에 나란히 넣어 비교, 와이파이 끄고 오프라인 시연

■ LoRA/QLoRA
- 기술적으로 가능: 1~3B 모델, MLX(mlx-lm) LoRA로 M5 Pro에서 약 1시간 안팎
  (정석 QLoRA/bitsandbytes는 NVIDIA 기준 → 맥은 MLX 양자화+LoRA, 또는 Colab)
- 병목은 데이터: 정답 데이터 없음 → 합성 데이터는 큰 모델의 실수까지 학습
- 가르칠 것: 행동/형식(JSON 준수, 판단 보류, 과장 금지) / 가르치면 안 될 것: 의학 지식(RAG 담당)
- 선택 확장으로만: LoRA 없이도 완성되게, 시간 남으면 평가표에 한 줄 추가
- 대회 전 사전 작업 허용 범위는 공식 규칙에서 확인 필요
