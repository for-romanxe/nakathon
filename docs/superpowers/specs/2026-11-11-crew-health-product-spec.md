# Crew Health 제품 명세 (v1, 2026-11-11)

NASA Space Apps Challenge 2026 Seoul · 챌린지 "Create Health Monitoring Software for Astronauts on Space Missions" · 팀 4인.
이 문서는 행사(11/14 09:00 ~ 11/15 23:59)에서 무엇을 만들지 정한 명세다. 코드·디자인·슬라이드·영상은 행사 전에 만들지 않는다(서울 규칙). 이 문서와 조사 노트, 회의용 목업(`mockup/app/`)은 준비물이다.

표기: **[결정]** 사용자·팀이 정한 것. **[내 판단]** 빌더가 바꿔도 되는 제안. **[미정]** 아직 정하지 않은 것.

## 1. 한 줄 정의

우주비행사가 이미 하는 건강 루틴을 한곳에서 가볍게 돌리고, 몸 상태에 따라 오늘 할 일을 바꿔 주는 **기기 안 관리 시스템**. 판단은 규칙이, 설명은 작은 언어모델(SLM)이, 검증은 코드가 한다.

## 2. 왜 (의도)

- 장기 임무에서는 승무원이 스스로 몸의 변화를 알아채야 한다(챌린지 본문). 지구 의료진은 있지만 즉시 답할 수 없다.
- 기존 접근은 "수치 대시보드 + AI 경고"다. 우리는 **오늘 할 일**을 먼저 주고, 그 근거(수치·규칙 판정·출처·검증 결과)를 나란히 보여준다.
- 모델은 판단하지 않는다. 그래서 틀려도 판정은 안 바뀌고, 틀린 설명은 버려진다.

## 3. 임무 배경 **[결정]**

- 기본: **화성** 왕복·화성 기지. 편도 지연 3~22분, 통신 창 하루 2~4회, 태양 합 때 약 2주 두절(일반 지식, 출처 미확인).
- 발표에서는 "달·ISS 등 다른 임무에서도 그대로 쓴다"고 말한다. 통신 지연·창은 설정값이라 바꾸면 된다.
- 승무원 4명. A(비행 엔지니어, 데모 주인공), B(CMO·사령관, 의사 아님), C(과학, 기준선 수집 중), D(조종사, 참고 사례).

## 4. 목표 / 비목표 / 실패 조건

**목표**
- 승무원 A가 아침에 열면 10초 안에 "오늘 이렇게 한다"를 안다.
- 이상이 없는 날에도 화면이 할 말이 있다(루틴).
- 증상을 문장으로 적으면 코드 → 판정 → 위험 안내 3줄 → 검증 결과 → 할 일까지 한 흐름으로 나온다.
- 모델이 틀린 설명을 코드가 잡아내는 장면을 데모에서 보여준다.
- 평가 숫자(검증기 폐기율, 증상 분류 정확도)를 발표에 넣는다.

**비목표**
- 실제 의료 진단·처방. 지구 LLM. 실시간 스트리밍 바이탈. 얼굴 인증·표정 인식·그림 심리. 점수·배지형 게임화. 수분 섭취 상세 기록.

**실패 조건**
- 지표 하나가 하루 벗어났다고 노란 배너가 뜬다(과경보).
- 아침 체크인이 30초를 넘는다.
- 모델 문장이 규칙 판정보다 세게 말하는데 화면에 그대로 나간다.
- 출처 없는 문장이 화면에 나간다.

## 5. 제약

- 서울 규칙: 산출물 사전 제작 금지, 준비 허용. 모델 사전 학습·환경 설치·자료 수집은 허용(사용자 확인 11/11). 출처·라이선스 표기 필수. 비NASA 자료는 공개·오픈소스여야 하고, 우리 산출물은 오픈소스로.
- 행사 시간 약 36시간, 4명. 팀 미팅 1회(카메라 on), 개인 체크인 5회 중 4회, 11/15 23:55 제출 권장.
- 회의용 목업(`mockup/app/`)은 **참고만 한다. 코드·CSS·규칙 로직은 행사 중 새로 짠다** **[결정]**. 구조·토큰 값·규칙 표는 보고 베껴도 되지만 파일을 복사하지 않는다.
- 기기 안 실행: 노트북 한 대에서 프론트·백엔드·모델이 모두 돈다. 네트워크 없이 데모 가능해야 한다.
- 개발·데모 기기 **[결정]**: Tyler PC(Intel i5-11500, RTX 3060 12GB, RAM 32GB, Windows 11 Pro)와 Mac M5 Pro 24GB 둘 다 쓴다. 4B는 어느 쪽이든 여유, 11B급은 양자화(Q4)로 양쪽에서 가능. 팀원 기기에서는 모델 mock 모드로 개발한다(§18).
- 모델 응답 1~2초는 정상이고 화면에 보여준다.
- 데이터는 프록시(지구 데이터)임을 화면에 표시한다. 가상 문서·가상 승무원임을 표시한다.

## 7. 화면 구조 **[결정]**

좌측 레일 6 + 설정 + 상세 2. 각 화면은 라우트 하나.

1. **오늘** — 인사 → 상태 한 문장(색) → **오늘의 가이드** → 근거(지표 6 타일 + 작은 픽셀 바디) → 오늘 이벤트 → 체크인 연속 일수. 첫 진입 시 아침 체크인 시트가 위에 뜬다.
2. **몸** — 픽셀 바디 크게 + 부위 목록 + 부위 상세. 이상 부위는 셀이 흩어지고 클릭하면 상세.
3. **추세** — 지표별 7/30/90일, 기준선 ±2σ·±3σ 밴드, 이벤트 마커, 요약표, 장기 지표(골밀도·방사선·체중·안압).
4. **기록** — 증상·약·기분 대화(모델이 끼는 유일한 입력), 체크인 설문, 정기 기록(주간·월간·분기 양식), 이벤트 목록, 활동 로그.
5. **절차서** — 기기 안 문서 목록·검색·문단 하이라이트. 설명 속 출처 id가 여기로 링크.
6. **승무원** — CMO 전용. 4명 카드(바디·기준선·벗어난 지표·열린 이벤트), 지구 전송 큐, 무시 기록, 활동.
7. **설정** — 기준선 창·민감도·알림·열람 권한·전송 창·임무 배경(통신 지연·창)·언어·모델 정보·데모 전환·초기화.
- **이벤트 상세** — 보고 문장 · 사실(규칙 표) · 위험 안내 3줄(모델) · 검증(코드 5칸) · 대응 체크리스트 · 공유·전송·무시 · 파이프라인 시간.
- **경보 화면** — 전체 화면. 절차서 첫 단계, 지금 수치, CMO 호출, 지구 긴급 전송, 경보 확인, 오경보 종결(이유 필수).

UI 언어: **한국어·영어 토글** **[결정]**. 모든 문자열은 사전 파일(ko/en)로. 모델 프롬프트·출력도 언어별로.

디자인: `DESIGN.md` 토큰 유지. 성격은 "아침마다 말 거는 관리자". 초록=정상, 노랑=주의, 빨강=경보, 참고는 무색. 평평함·헤어라인·카드 중첩 금지·출처는 파랑·숫자는 모노.

## 10. 규칙 엔진 (판정은 여기서만) **[결정]**

- **기준선**: 승무원별로 오늘 이전에 측정값이 있고 이벤트가 없었던 최근 14일의 평균·표준편차. 14일 미만이면 판정 없음("보류"), 측정값만 기록. 비행 전 기준선은 비교선으로만.
- **z = (측정 - 평균)/sd**. 민감도 설정: 표준 2σ/3σ, 민감 1.8/2.6, 둔감 2.3/3.3.
- **경보 계층**
  - 정상: 6지표 모두 |z| < 2. 설명 생성 안 함.
  - 참고(advisory): 지표 1개가 하루 |z| ≥ 2. 색·배지 없음. 가이드에 한 줄.
  - 주의(caution): 이틀 연속 **또는** 지표 2개 이상 **또는** 지표 1개 + 증상 보고. 노란 상태 문장 + 레일 배지 + 가이드 조정. 인터럽트 없음.
  - 경보(warning): 증상 규칙(흉통·호흡곤란·의식 변화·위기 표현) **또는** |z| ≥ 3. 전체 화면, 소리, 모델 건너뜀, 지구 긴급 전송.
    - **[11/14 보강, `docs/CONTRACT.md` §5.4와 같은 규칙]** 경보는 원인과 상관없이 똑같이 다룬다. 즉시 경보 증상 없이 측정값만 |z| ≥ 3인 경우에도 **전체 화면 경보를 띄우고 모델을 건너뛴다.** 가장 높은 단계에서는 고정된 절차서와 수치만 보여 주고, 생성 문장을 기다리지 않는다.
    - 경보의 원인이 보고 문장(증상 규칙)인지는 이벤트의 `urgent`로 표시한다. 화면은 경보 여부(전체 화면, 모델 건너뜀 안내)를 `level`로, 원인 문구("긴급 증상" / "측정값이 크게 벗어남")를 `urgent`로 고른다.
    - 증상 보고의 등급은 **보고마다 따로** 계산한다. 그 보고 문장에 건 증상 규칙과 보고 시점의 지표만 쓰고, 그날 전체 상태나 다른 보고의 등급은 물려받지 않는다. 예: 흉통 보고 뒤의 두통 보고는 지표가 정상이면 정상이고, 모델을 건너뛰지 않는다.
- **증상 규칙(모델보다 먼저)**: 키워드 사전(가슴·흉통·숨·호흡곤란·의식·죽고 싶 등 ko/en). 매치 시 즉시 경보. 모델은 경보를 올릴 수만 있고 낮출 수 없다.
- **가이드 조정 규칙**(예시, 빌더가 표로 확장)
  - 주의 + 심박↑ 또는 HRV↓ → 운동 "저강도 1시간, 운동 중 심박 안정 시 +40 이내" (hrp:sm-03#p5)
  - 수면 < 기준 - 1.5h → "정밀 작업 오전 늦게, 카페인 정오 전까지" (hrp:sleep-02#p2)
  - 어지러움 보고 → 임시 항목 "수분 500 mL + 염분", "30분 뒤 심박 재측정", "14:00 기립 재확인"
  - 이벤트 날은 기준선 계산에서 제외
- **무시(override)**: 이유 선택 필수(운동 직후·착용 불량·조치 완료·기타), 기록에 남고 CMO에 보임.
- **스케줄**: 주간·월간·분기 항목의 다음 날짜 계산, 가이드에 해당 날만 표시.

## 11. 모델(SLM)의 자리 **[결정]**

모델은 기기 안 Qwen 계열. **어떤 모델을 쓸지는 사용자(AI 파트)가 정한다** **[결정]**. 기본은 **바닐라 모델 + Ollama structured outputs(JSON 스키마·enum 제약)**이고, 행사 전 파인튜닝은 업그레이드다: 제때 나오면 Modelfile로 교체, 늦으면 바닐라 그대로 **[결정]**. 팀은 개발 중 바닐라로 맞춘다. 크기(4B vs 11B급)는 행사 중 같은 질문셋으로 비교 **[미정]**.

| 자리 | 입력 | 출력(형식 고정) | 범위 |
|---|---|---|---|
| ① 증상 알아듣기 | 자유 문장 + 최근 수치 요약 | enum 제약 JSON: codes[](고정 목록), onset, worse_when, severity, needs_question | 1차 |
| ② 기분 문장 → 척도 | "오늘 꿀꿀해" | {mood:1-5, fatigue:1-5, stress:1-5, confidence} | 1차 |
| ③ 위험 안내·조정 이유 문장 | 규칙 판정 + findings + 검색 문단 + 조정 결과 | JSON {category, condition_id(고정 목록), lines[3], cites[]} — 숫자 문장은 템플릿이 쓰고 모델은 "왜·무엇을 조심" 1~2문장 | 1차 |
| ④ 약 안내 문장화 | 규칙이 계산한 표(용량·간격·남은 양·병용) + 문단 | 문장 + cites, 항상 "CMO 확인" | 1차 |
| ⑤ 물어보기 "왜요?" | 가이드 항목 + 질문 + 검색 문단 | 답 + cites, 없으면 abstain | **2차** |

모델이 하지 않는 것: 판정, 경보, 조정 결정, 목록 밖 상태 이름, 일정 계산, 주간 요약(표로).

**파이프라인(코드에 고정)**: 수집 → 규칙 판정 → [증상이면 ① → 확인 질문 1개] → 근거 검색(BM25, 기기 안 문서) → ③ 생성 → 검증 → 통과면 화면, 실패면 재생성(최대 2회) → 2회 실패면 "판단 보류"(수치·절차서만).

## 12. 검증 **[결정: 설계는 사용자(AI 파트) 담당]**

명세에는 인터페이스만 적는다. 검증기는 코드이고 5개 결과를 낸다.

| 검사 | 통과 조건 |
|---|---|
| 숫자 일치 | 문장 속 수치가 findings·baseline과 같다 |
| 출처 존재 | 모든 문장에 기기 안 문서 id가 있고 실제로 존재한다 |
| 판정 일치 | 문장의 강도가 규칙 판정을 넘지 않는다 |
| 형식 | JSON 스키마·enum 통과 |
| 목록 밖 이름 없음 + 단정 표현 없음 | 상태 이름은 고정 목록에서만, "입니다/확실/진단" 금지, "가능성"만. **[11/14 보강]** 문장에 쓸 수 있는 상태 이름은 규칙 엔진이 후보로 넘긴 것뿐이다. "움직입니다" 같은 동사와 "주의력"·"alertness"는 금지 표현이 아니다. 해요체의 단정("~이에요/~예요")과 "~입니다만"도 "입니다"와 같이 막는다 |

의미·인과 검사를 검사자 모델로 추가할지는 사용자 결정 **[미정]**. 루프 상한 2회 **[결정]**.

**데모 결함 주입** **[내 판단]**: 숫자 문장을 템플릿이 쓰면 모델이 숫자를 틀릴 일이 드물어 S3 장면이 자연 발생하지 않을 수 있다. 설정의 데모 구역에 "결함 주입" 토글(없음 / 숫자 틀림 / 출처 누락 / 단정 표현)을 두어 run 1에 해당 결함을 넣고 검증기가 잡는 장면을 재현한다. 발표에서는 주입임을 밝힌다. 평가(§19)에서는 주입 없이 자연 폐기율을 따로 잰다.

## 13. 기기 안 문서(RAG 코퍼스)

- **절차서**: HRP 공개 문서를 바탕으로 한 요약 문단(가상 id: hrp:sm-03 등). 실제 HRP Evidence Report 문단을 쓰면 출처 표기 **[미정: 11/13 Resources 확인 후]**.
- **상태 목록**: 10~15개(기립성 저혈압, 우주 멀미, 탈수, 수면 부족, CO2 두통, 근골격 통증, 상기도 감염, 피부 발진, 안압 상승 의심, 불안·기분 저하 등). 각각 HRP 범주·관련 지표·첫 대응·출처.
- **약 문서**: 비상상비약 10~15품목. 출처는 openFDA 라벨(영문) + 식약처 e약은요(한국어). 라이선스 원문 확인 **[미정]**. 항목: 보통 용량, 간격, 하루 최대, 병용 금기, 유효기간.
- **루틴 문서**: 일일 운동 2.5h, 수면 평가, 주간 식이·PMC, 월간 체질량(OCHMO 근거).
- **응급 절차**: 흉통·호흡곤란·위기 표현 대응.
- 검색: BM25(한국어 형태소 없이 bigram 또는 간단 토크나이저) **[내 판단]**. 문단 단위 id `doc#pN`.
- **코퍼스 언어** **[내 판단]**: 문단은 한국어 한 벌만 쓴다(제목은 ko/en). 영어 UI 모드에서는 모델이 한국어 문단을 근거로 영어 문장을 쓰고, cites는 같은 id를 가리킨다. 검증기는 숫자·id·금지 표현만 보므로 언어와 무관하게 동작한다(금지 표현 사전만 ko/en 두 벌). 데모·영상 기본 언어는 한국어 UI, 발표 자료는 영어.

## 14. 약 안내 **[결정]**

- 범위: 비상상비약만. 보통 용량·복용 간격·같이 먹으면 안 되는 것까지. 처방·진단·용량 조정 없음. 항상 "CMO와 확인해 주세요".
- 복용 기록 한 탭. 질문 시 규칙이 먼저 표 계산(마지막 복용 후 시간, 하루 최대까지 남은 양, 최근 복용 약과 병용 금기), 모델은 문장화만.
- 유효기간: 키트 품목에 유효기간, 지난 약이면 경고(ISS 보관 약 9종 중 4종만 기한 후 기준 충족).
- 수면제·각성제 류는 CMO 확인을 문장 맨 앞에.

## 15. 심리 **[결정]**

- 매일 기분·피로(아침)·스트레스(저녁) 눈금. 자유 문장은 모델이 척도로 변환해 눈금과 함께 저장.
- 위기 표현은 규칙으로 즉시 경보(옆 승무원·CMO 호출, 지구 긴급 큐). 모델이 낮출 수 없음.

## 16. 통신·지구 쪽 **[결정]**

- 모델은 기기 안에서만. 지구 LLM 없음. 지구 쪽은 비행의(사람) 검토 + 문서·규칙 업데이트.
- 전송 큐: 요약 먼저(하루 몇 KB), 원본은 요청 시. 경보 패킷은 즉시·같은 창 2~3회 반복, 주의는 다음 창, 일일 요약은 정기 창(설정 08:00/20:00).
- 모든 패킷 seq + hash, 추가 전용. 지상은 빠진 seq만 재요청. 상태: queued → sent → acked / missing.
- 상향: 비행의 답장(seq·ack), 문서·규칙 업데이트(서명·버전, 완전 수신 후 적용).
- **링크 시뮬레이터(2차)** **[내 판단]**: 승무원 화면의 전송 큐에 창 열림/닫힘 타이머, 손실률 슬라이더, 빠진 seq 재요청 표시. 프레임 손실까지 보여주되 DTN 구현은 안 함.
- 화면 표기: 편도 지연, 다음 창 시각, 응답 가능 시각.

## 17. CMO·승무원 화면 **[결정]**

- B(CMO)만 접근. 4명 카드, 열린 이벤트 링크, 지구 전송 큐, 무시 기록, 활동 로그, "승무원 라운드" 가이드 항목.
- 열람 권한은 설정에서 승무원이 켜고 끔(CMO 열람 기본 on, 다른 승무원 배지 열람 기본 off).

## 18. 기술 스택

- 프론트: **React + Vite** **[결정]**, 팀원 담당. 상태는 백엔드 API에서. 언어 토글은 i18n 사전(ko/en).
- 백엔드: **FastAPI(Python) + SQLite** **[내 판단, 사용자가 팀에 통지]**. 규칙 엔진·스케줄·RAG·검증·모델 호출·전송 큐 모두 여기.
- 모델 실행: **Ollama** **[결정]**, Qwen3 4B 또는 11B급 **[미정]**, structured outputs(JSON schema)로 enum 제약.
- **모델 mock 모드** **[내 판단]**: 백엔드 환경변수 `MODEL=mock`이면 고정 응답(시나리오별 JSON)을 1초 지연으로 돌려준다. 프론트·백엔드 담당은 Ollama 없이 개발한다. 파이프라인 단계 진행은 SSE로 보낸다(mock에서도 동일).
- 배포: 노트북 한 대, `localhost`. 오프라인 데모 가능. 저장소는 공개 GitHub(오픈소스 라이선스, 예: MIT) **[내 판단]**.
- 데이터 적재: CSV(E4·Sleep-EDF 가공) → SQLite. 시간은 Sol 단위 가상 시계 + 실제 시각 오프셋.

**API 초안** **[내 판단]**
